# Decisions

One line per decision: what was chosen, why, and what was rejected. Rewrite the reasons in your own words as you learn them, because these become your report and your viva answers. Add the date for every new entry.

- 2026-11-05: Build a multi-tenant support ticket intelligence platform. Reason: it is a real product category, mixes software engineering with ML, and matches my work in technical support. Rejected: crop disease detection, scam message detector, and other single-model projects, because they are not platforms.
- 2026-11-05: One shared database with a `tenant_id` on every row. Reason: simplest design that is still multi-tenant, and cheap on a free tier. Rejected: a database or schema per tenant, which is heavier to run and migrate.
- 2026-11-05: Supabase hosted PostgreSQL as the database (my choice). Reason: free, uses no RAM on my low-spec PC, and supports pgvector. Trade-offs: needs an internet connection, free projects pause after 1 week of inactivity, 500 MB size limit, no automatic backups.
- 2026-11-05: Job queue is a `jobs` table claimed with `FOR UPDATE SKIP LOCKED`. Reason: no extra service to run. Rejected: Redis and Celery, which cost memory my machine does not have.
- 2026-11-05: Own login and API-key system instead of Supabase Auth. Reason: I can explain every part in the viva. Rejected: Supabase Auth, which is faster to build but hides the interesting parts.
- 2026-11-05: Reply drafting uses a hosted LLM (Gemini or Groq free tier) behind a provider interface, and it is optional. Reason: no local LLM fits my PC, and free limits can change. Rejected: running a local model with Ollama.
- 2026-11-05: Server-rendered pages with Jinja2 and HTMX for the dashboard. Reason: avoids a Node dev server eating RAM. Rejected: a React single-page app.
- 2026-11-05: Phase 1 includes a minimal ticket create and list. Reason: the isolation test needs tenant-owned data before the queue exists. Ticket creation returns `202` already so the contract does not change in phase 2.
- 2026-11-05: Connection pool uses `psycopg_pool.ConnectionPool` with `open=False` and lifecycle tied to FastAPI lifespan. Reason: prevents network I/O and blocking at import time, ensures bounded timeout on startup failure, and cleanly shuts down connections. Rejected: `NullConnectionPool` (which does not pool connections) and connecting at module import.
- 2026-11-05: Security operations use Argon2 for passwords, PyJWT with explicit algorithm whitelist ["HS256"] and UUID claim validation, and SHA-256 for API keys. Reason: Argon2 is resistant to GPU cracking and provides automatic salt generation; explicit HS256 prevents algorithm downgrade attacks; SHA-256 for API keys is standard one-way storage. Rejected: bcrypt (Argon2 is modern standard in SPEC.md) and storing plaintext API keys.
- 2026-11-05: Clarify repository tenant_id rule for pre-auth entry points. Reason: creating a tenant at signup and looking up user by normalized email at login occur before a tenant credential exists; dedicated, narrowly-scoped functions handle these without accepting caller-supplied tenant IDs. Rejected: allowing client requests to specify arbitrary tenant IDs or bypassing repository encapsulation.
- 2026-11-05: Test database isolation uses canonical target resolution and CI service containers. Reason: prevents catastrophic accidental test runs against production/development database targets by comparing parsed host/port/dbname rather than raw strings, and uses throwaway PostgreSQL services in GitHub Actions. Rejected: running integration tests against DATABASE_URL or mocking PostgreSQL in integration tests.
- 2026-11-05: API key revocation is idempotent using COALESCE(revoked_at, NOW()) with tenant_id filtering. Reason: repeat revocation by the key owner should safely return 204 without altering the original revocation timestamp; cross-tenant attempts match 0 rows and return 404 to avoid leaking key existence. Rejected: hard-deleting API key rows or returning 403 on cross-tenant attempts.
- 2026-11-05: Ingest idempotency uses ON CONFLICT (tenant_id, external_id) WHERE external_id IS NOT NULL DO NOTHING returning 202 for new tickets and 200 for existing tickets. Reason: guarantees crash resilience and avoids duplicate tickets or 500 crashes during network retries, while strictly scoping external IDs per tenant. Rejected: returning 409 conflict on duplicate external IDs or global uniqueness across tenants.
- 2026-11-05: Ticket read endpoints support dual credential resolution (X-API-Key or Authorization Bearer), while ticket ingestion is API-key only and admin routes remain JWT-only. Reason: allows both automated integrations and human dashboards to query tickets safely, while preventing human JWT sessions from spoofing ingest systems or API keys from touching admin configurations. Rejected: permitting JWT on ingestion or allowing API keys to manage keys/tenants.
- 2026-11-05: Return plain JSON array for GET /v1/tickets. Reason: strictly follows SPEC.md Section 7 contract and keeps client consumption minimal. Rejected: wrapping in {"items": [...], "limit": N, "offset": M} envelope.
- 2026-11-05: Dual-header requests give strict precedence to X-API-Key with no fallback. Reason: guarantees single-source identity resolution and prevents credential-mixing or security masking across headers. Rejected: merging tenant/user from different headers or silently falling back to Authorization on invalid API keys.
