# Decisions

One line per decision: what was chosen, why, and what was rejected. Rewrite the reasons in your own words as you learn them, because these become your report and your viva answers. Add the date for every new entry.

- 2026-11-05: Build a multi-tenant support ticket intelligence platform. Reason: it is a real product category, mixes software engineering with ML, and matches my work in technical support. Rejected: crop disease detection, scam message detector, and other single-model projects, because they are not platforms.
- 2026-11-05: One shared database with a `tenant_id` on every row. Reason: simplest design that is still multi-tenant, and cheap on a free tier. Rejected: a database or schema per tenant, which is heavier to run and migrate.
- 2026-11-05: Supabase hosted PostgreSQL as the database (my choice). Reason: free, uses no RAM on my low-spec PC, and supports pgvector. Trade-offs: needs an internet connection, free projects pause after 1 week of inactivity, 500 MB size limit, no automatic backups.
- 2026-11-05: Job queue is a `jobs` table claimed with `FOR UPDATE SKIP LOCKED`. Reason: no extra service to run. Rejected: Redis and Celery, which cost memory my machine does not have.
- 2026-11-05: Own login and API-key system instead of Supabase Auth. Reason: I can explain every part in the viva. Rejected: Supabase Auth, which is faster to build but hides the interesting parts.
- 2026-11-05: Reply drafting uses a hosted LLM (Gemini or Groq free tier) behind a provider interface, and it is optional. Reason: no local LLM fits my PC, and free limits can change. Rejected: running a local model with Ollama.
- 2026-11-05: [Superseded on 2026-11-06] Server-rendered pages with Jinja2 and HTMX for the dashboard. Reason: initial preference to avoid a Node dev server eating RAM. Superseded on 2026-11-06 by React + Vite + TypeScript frontend communicating via dedicated /browser-api/* JSON endpoints with static FastAPI production serving. Rejected: maintaining dual template and SPA rendering.
- 2026-11-05: Phase 1 includes a minimal ticket create and list. Reason: the isolation test needs tenant-owned data before the queue exists. Ticket creation returns `202` already so the contract does not change in phase 2.
- 2026-11-05: Connection pool uses `psycopg_pool.ConnectionPool` with `open=False` and lifecycle tied to FastAPI lifespan. Reason: prevents network I/O and blocking at import time, ensures bounded timeout on startup failure, and cleanly shuts down connections. Rejected: `NullConnectionPool` (which does not pool connections) and connecting at module import.
- 2026-11-05: Security operations use Argon2 for passwords, PyJWT with explicit algorithm whitelist ["HS256"] and UUID claim validation, and SHA-256 for API keys. Reason: Argon2 is resistant to GPU cracking and provides automatic salt generation; explicit HS256 prevents algorithm downgrade attacks; SHA-256 for API keys is standard one-way storage. Rejected: bcrypt (Argon2 is modern standard in SPEC.md) and storing plaintext API keys.
- 2026-11-05: Clarify repository tenant_id rule for pre-auth entry points. Reason: creating a tenant at signup and looking up user by normalized email at login occur before a tenant credential exists; dedicated, narrowly-scoped functions handle these without accepting caller-supplied tenant IDs. Rejected: allowing client requests to specify arbitrary tenant IDs or bypassing repository encapsulation.
- 2026-11-05: Test database isolation uses canonical target resolution and CI service containers. Reason: prevents catastrophic accidental test runs against production/development database targets by comparing parsed host/port/dbname rather than raw strings, and uses throwaway PostgreSQL services in GitHub Actions. Rejected: running integration tests against DATABASE_URL or mocking PostgreSQL in integration tests.
- 2026-11-05: API key revocation is idempotent using COALESCE(revoked_at, NOW()) with tenant_id filtering. Reason: repeat revocation by the key owner should safely return 204 without altering the original revocation timestamp; cross-tenant attempts match 0 rows and return 404 to avoid leaking key existence. Rejected: hard-deleting API key rows or returning 403 on cross-tenant attempts.
- 2026-11-05: Ingest idempotency uses ON CONFLICT (tenant_id, external_id) WHERE external_id IS NOT NULL DO NOTHING returning 202 for new tickets and 200 for existing tickets. Reason: guarantees crash resilience and avoids duplicate tickets or 500 crashes during network retries, while strictly scoping external IDs per tenant. Rejected: returning 409 conflict on duplicate external IDs or global uniqueness across tenants.
- 2026-11-05: Ticket read endpoints support dual credential resolution (X-API-Key or Authorization Bearer), while ticket ingestion is API-key only and admin routes remain JWT-only. Reason: allows both automated integrations and human dashboards to query tickets safely, while preventing human JWT sessions from spoofing ingest systems or API keys from touching admin configurations. Rejected: permitting JWT on ingestion or allowing API keys to manage keys/tenants.
- 2026-11-05: Return plain JSON array for GET /v1/tickets. Reason: strictly follows SPEC.md Section 7 contract and keeps client consumption minimal. Rejected: wrapping in {"items": [...], "limit": N, "offset": M} envelope.
- 2026-11-05: Dual-header requests give strict precedence to X-API-Key with no fallback. Reason: guarantees single-source identity resolution and prevents credential-mixing or security masking across headers. Rejected: merging tenant/user from different headers or silently falling back to Authorization on invalid API keys.
- 2026-11-05: Temporary Phase-Gate Exception for GitHub CI billing lock. Reason: GitHub account billing lock blocks CI jobs before start; approved running full local PostgreSQL test suite against TEST_DATABASE_URL to gate development into Phase 2 while keeping CI verification explicitly outstanding. Rejected: changing application code/CI configs to bypass billing or claiming CI passed.
- 2026-11-05: Jobs table uses composite foreign key (tenant_id, ticket_id) REFERENCES tickets(tenant_id, id) with UNIQUE (tenant_id, ticket_id, type). Reason: enforces multi-tenant integrity at the database schema level and guarantees at most one ingestion job per ticket across all states. Rejected: referencing ticket_id alone or allowing multiple concurrent/completed duplicate jobs.
- 2026-11-05: Worker claim ownership uses generation counter (attempts) and renewable 300s lease. Reason: prevents split-brain and stale worker completion after timeout without relying on wall-clock heartbeat timestamps alone; renewal checks reject already-expired leases. Rejected: using mutable locked_at as sole claim check.
- 2026-11-05: Phase 2 worker conditionally transitions tickets from new to open without content normalization. Reason: preserves raw customer subject/body intact and avoids reopening tickets that were already resolved or progressed by agents. Rejected: overwriting stored ticket text or reopening non-new tickets.
- 2026-11-05: Worker claim and recovery use narrowly scoped platform-level repository exceptions with optional tenant_id. Reason: background worker must poll across all tenants to service the shared queue, while tests need tenant-scoped claiming to prevent draining unrelated test fixtures. Rejected: requiring tenant_id for global worker claim or letting tests drain random queue jobs.
- 2026-11-05: Worker job finalization commits ticket state transition and job completion in a single short transaction. Reason: guarantees zero side-effects if lease expires or claim generation is preempted. Rejected: updating ticket before verifying claim or holding long database transactions open during processing.
- 2026-11-05: CSV bulk ticket ingestion uses chunked request.stream() reading with actual byte-counter enforcement, whole-file pre-validation, standard-library csv module, and single-transaction commit per batch. Reason: genuinely bounds memory by aborting immediately above 5 MB regardless of Content-Length header presence or chunked transfer encoding, rejects malformed or invalid rows upfront with 422 to avoid dirty partial imports, and guarantees atomic creation of tickets and matching jobs while safely replaying duplicate external_ids with zero external dependencies. Rejected: relying solely on Content-Length, adding multipart dependencies, batch-job orchestration tables, or committing partial successful rows on invalid files.
- 2026-11-05: Phase 3 ML model integration uses model_versions and ticket_predictions with composite foreign keys (tenant_id, ticket_id) and (tenant_id, model_version_id). Reason: guarantees multi-tenant database-level referential integrity, idempotency on retries via UNIQUE (tenant_id, ticket_id, task), and keeps automated category predictions distinct from human-curated ticket category fields. Rejected: overwriting tickets.category directly with model output or allowing nullable/cross-tenant foreign keys.
- 2026-11-05: Shared ML models are registered per-tenant in model_versions with tenant_id NOT NULL. Reason: strictly adheres to SPEC.md Section 5 & 6 tenant isolation and repository rules without introducing undocumented global-tenant queries or bypasses. Rejected: global model_versions table with tenant_id NULL.
- 2026-11-05: LinearSVC confidence is left strictly NULL while raw decision scores (hyperplane margins) are stored in JSONB. Reason: decision scores and softmax transforms of SVM margins are not calibrated posterior probabilities. Rejected: pretending raw margins or pseudo-probabilities represent calibrated confidence.
- 2026-11-05: Worker preloads trusted local model artifact once per process using SHA-256 integrity and structural validation. Reason: avoids costly disk I/O and deserialization per ticket while strictly preventing arbitrary untrusted model execution, and fails with explicit operational errors (not fabricated predictions) if missing or corrupted. Rejected: deserializing models per ticket or downloading arbitrary model weights from untrusted URLs.
- 2026-11-06: Frontend uses React + Vite + TypeScript communicating via dedicated /browser-api/* JSON endpoints with HttpOnly session cookies and session-bound CSRF protection, built into static assets served directly by FastAPI in production without a production Node server. Reason: provides modern interactive UI with clean component boundaries and zero JavaScript-accessible JWTs, while avoiding a Node server in production. Rejected: Jinja2 server-rendered templates, storing tokens in localStorage/sessionStorage, and broad CORS configurations.
- 2026-11-06: Browser API enforces 32 KiB raw request-body limit via chunked byte-counter stream reading before JSON deserialization. Reason: genuinely bounds memory and prevents DoS via huge payload strings or whitespace without relying solely on Content-Length headers, returning standardized HTTP 413 JSON error with Cache-Control: no-store. Rejected: relying on Pydantic field length bounds alone after whole-body in-memory deserialization.
- 2026-11-06: Browser UI extended from read-only inspection to include authenticated ticket submission via dedicated POST /browser-api/tickets. Reason: eliminates need for external curl/PowerShell tooling when demoing financial complaint triage, while maintaining strict browser session authentication, session-bound CSRF protection, 32 KiB raw body limit, and asynchronous background worker classification. - 2026-11-06: Accurate ticket-processing status derivation and error sanitization in browser responses. Reason: gives operators transparent visibility into real queue states (`queued`, `processing`, `retry_scheduled`, `completed`, `failed`, `not_found`), separates prediction availability from background execution (preventing failed or completed-without-prediction tickets from being mislabeled "pending"), prevents N+1 queries in the ticket list via single SQL JOIN with `jobs`, and strictly sanitizes raw database errors, worker IDs, and credentials from browser responses with safe generic explanations. Rejected: exposing raw job error strings/traces to browser clients, running per-ticket SQL queries in list views, polling/WebSockets, or fabricating prediction statuses.
